## Level 15 → 16 — з'єднання через SSL

**Завдання:** надіслати пароль поточного рівня на порт 30001 на `localhost`, але з'єднання має бути зашифроване (SSL/TLS).

**Хід думок:**
1. На минулому рівні вистачило `nc`. Але `nc` передає текст як є, без шифрування, а служба на 30001 чекає TLS-рукостискання. Потрібен клієнт, який уміє шифрувати, — `openssl s_client`.
2. Підключився й вставив пароль. Замість відповіді побачив `KEYUPDATE`. Виявилось, що в інтерактивному режимі `s_client` сприймає рядки, які починаються з `k`, `Q` або `R`, як власні команди, а пароль починався саме з `k`.
3. Опція `-quiet` вимикає цю поведінку й зайвий вивід про сертифікат:

```bash
openssl s_client -connect localhost:30001 -quiet
# вставити пароль → Correct! <пароль>
```

**Що вивчив:**
- Шифрування захищає дані в дорозі, але не вирішує, **хто** має доступ. Це різні речі: шифрування і контроль доступу.
- Сертифікат на сервері самопідписаний (`SnakeOil`), тобто ніхто його не засвідчив. Для навчального сервера нормально, для реального сайту — червоний прапорець.
- Якщо програма поводиться дивно на певних даних, варто перевірити, чи вона не трактує їх як команди.

## Level 16 → 17 — пошук потрібного порту

**Завдання:** на `localhost` у діапазоні портів 31000–32000 знайти той, що працює через SSL і віддає пароль (а не просто повторює введене), і надіслати туди пароль поточного рівня.

**Хід думок:**
1. Перебирати тисячу портів вручну немає сенсу — потрібен сканер, `nmap`.
2. Написав `nmap -p -sV 31000-32000 localhost`. `nmap` сприйняв `-sV` як значення для `-p`, і діапазон портів «загубився». Значення має стояти одразу після своєї опції.
3. Правильний порядок знайшов кілька відкритих портів, а `-sV` визначив, що на них працює:

```bash
nmap -sV -p 31000-32000 localhost
```

4. Частина портів — `echo` (повертає надіслане), частина — `ssl/echo`, і лише один — `ssl/unknown`. Логіка: echo пароль не віддасть, без SSL не підходить за умовою, отже потрібен той, де служба SSL, але `nmap` не впізнав, що за нею.
5. Надіслав пароль у цей порт:

```bash
echo <пароль> | openssl s_client -connect localhost:<порт> -quiet
```

6. У відповідь прийшов не пароль, а приватний SSH-ключ. Скопіював його з екрана у файл на віртуалці, дав `chmod 600`, але ssh видав `error in libcrypto`: ключ скопіювався з пошкодженнями. Ключ має збігатися до символу, включно з першим і останнім рядком (`-----BEGIN ...` / `-----END ...`). Після акуратного копіювання вхід спрацював:

```bash
chmod 600 ssh17
ssh -i ssh17 bandit17@bandit.labs.overthewire.org -p 2220
```

**Що вивчив:**
- `nmap -p` — які порти сканувати (діапазон `31000-32000` або список через кому).
- `-sV` не вгадує за номером порту: `nmap` читає банер служби або надсилає тестові дані й порівнює відповідь зі своєю базою сигнатур.
- Опція і її значення завжди стоять разом.
- Сканувати можна лише ті цілі, на які є дозвіл. Тут це навчальний сервер і його `localhost`.
- `echo текст | команда` — спосіб передати дані в програму без ручного введення.

## Level 17 → 18 — різниця між файлами

**Завдання:** у домашній папці два файли, `passwords.old` і `passwords.new`. Пароль — єдиний рядок, що змінився в `passwords.new`.

**Хід думок:**
1. Хотів передати `diff` два файли й написав `diff -q passwords.old > passwords.new`. Отримав `Operation not permitted`. Виявилось, що `>` — не розділювач між файлами, а перенаправлення: оболонка спробувала очистити `passwords.new` і записати туди вивід `diff`. Файл уцілів лише тому, що на сервері в мене немає права на запис. На своїй машині я б його стер.
2. Аргументи розділяються пробілом:

```bash
diff passwords.old passwords.new
# 42c42
# < (рядок зі старого файлу)
# ---
# > <пароль>
```

3. `42c42` — змінено рядок 42. `<` — рядок з першого файлу, `>` — з другого. Потрібен новий файл, отже рядок із `>`.

**Що вивчив:**
- `diff` порівнює файли рядок за рядком. У SOC так порівнюють конфіги до і після інциденту.
- `>` у команді означає «запиши сюди», і файл очищається ще до запуску команди. Той самий урок, що з `xxd -r data.txt > data.txt` на рівні 12.

## Level 18 → 19 — «Byebye!» при вході

**Завдання:** пароль у файлі `readme` у домашній папці, але хтось змінив `.bashrc` так, що при вході по SSH сесія одразу закривається.

**Хід думок:**
1. Зайшов звичайно — побачив `Byebye!`, і з'єднання закрилося. Пароль правильний, просто оболонка сама завершилась.
2. `.bashrc` — скрипт, який bash виконує при кожному запуску **інтерактивної** оболонки. У нього дописали команду виходу.
3. Отже, треба прочитати файл, не відкриваючи інтерактивної оболонки. SSH уміє виконати на сервері одну команду й відключитися — її пишуть у кінці:

```bash
ssh bandit18@bandit.labs.overthewire.org -p 2220 cat readme
# <пароль>
```

**Що вивчив:**
- `.bashrc` — налаштування терміналу: аліаси, вигляд запрошення, змінні. Лежить у домашній папці й прихований.
- `ssh user@host команда` виконує лише цю команду, без інтерактивної оболонки, тому `.bashrc` не спрацьовує.
- У SOC `.bashrc` і `.profile` перевіряють під час розслідування: дописаний туди рядок виконується при кожному вході користувача, тому це популярне місце для закріплення зловмисника.

## Level 19 → 20 — setuid

**Завдання:** скористатися setuid-програмою в домашній папці, щоб прочитати пароль у `/etc/bandit_pass/bandit20`.

**Хід думок:**
1. Спершу хотів знайти setuid-файли через `find . -perm`, але не знав, яке значення дати `-perm`. Сама ідея правильна: setuid-файли шукають так — `find / -perm -4000 2>/dev/null`.
2. `file bandit20-do` показав `setuid ELF 32-bit executable`. У `ls -la` права `-rwsr-x---`, власник `bandit20`, група `bandit19`: я в групі, тому можу запустити, а `s` замість `x` у власника означає, що програма працює з правами власника.
3. Запустив без аргументів — програма сама пояснила: `Run a command as another user. Example: ./bandit20-do whoami`.
4. Отже, будь-яка команда після неї виконується від імені bandit20:

```bash
./bandit20-do cat /etc/bandit_pass/bandit20
# <пароль>
```

**Що вивчив:**
- У процесу є **real UID** (хто запустив) і **effective UID** (з чиїми правами працює). Setuid робить effective UID рівним власнику файлу, а доступ до файлів система перевіряє саме за ним.
- Навіщо це існує: `passwd` належить root і має setuid, щоб звичайний користувач міг змінити свій пароль у `/etc/shadow`.
- Небезпечно не саме `s`, а поєднання: setuid + власник із ширшими правами + програма, що вміє робити довільні дії. `bandit20-do` виконує будь-яку команду, тобто фактично віддає права bandit20. Якби власником був root — це було б підвищення привілеїв.
- Незнайому програму спершу запускати без аргументів і читати, що вона приймає.

## Level 20 → 21 — я сервер

**Завдання:** setuid-програма `suconnect` підключається до `localhost` на порт, указаний в аргументі, читає рядок і, якщо це пароль bandit20, надсилає пароль bandit21.

**Хід думок:**
1. Досі клієнтом був я, а тут клієнт — програма. Отже, мені треба бути сервером: запустити щось, що **слухає** порт. `nc -l`.
2. Відкрив два термінали, в обох — bandit20. Спершу `nc -l 30000` — `Address already in use`. На порту 30000 уже працює служба з рівня 14; на одному порту може слухати лише одна програма. Взяв випадковий вільний.
3. У другому вікні написав `./suconnect nc -l 55555` — `Servname not supported`. Переніс схему з минулого рівня, де програма приймала команду. Але `suconnect` приймає лише порт і підключається сам; першим аргументом він отримав слово `nc` і спробував сприйняти його як порт.
4. Правильно — слухач в одному вікні, програма з тим самим портом в іншому:

```bash
# вікно 1
nc -l 55555
# вікно 2
./suconnect 55555
# у вікні 1 вставити пароль bandit20 → приходить <пароль>
```

**Що вивчив:**
- Клієнт ініціює з'єднання, сервер слухає порт і чекає. `nc -l` робить сервером будь-кого.
- `Address already in use` — порт зайнятий іншою програмою.
- Кожна програма має свій формат аргументів; не переносити звичку з попередньої.
- Так працює **reverse shell**: атакувальник слухає порт, а заражена машина сама підключається до нього, бо вихідні з'єднання фаєрволи часто пропускають. Сервер, що сам ініціює з'єднання на дивний порт назовні, — привід для перевірки в SOC.

## Команди, вивчені за рівні 15–20

- `openssl s_client -connect host:порт -quiet` — з'єднання через SSL/TLS
- `nmap -p 31000-32000 host` — сканування діапазону портів
- `nmap -sV -p ... host` — визначення служб на портах
- `echo текст | команда` — передати текст у програму
- `diff файл1 файл2` — різниця між файлами
- `ssh user@host -p порт команда` — виконати одну команду на сервері
- `ls -la` + `s` у правах — setuid; `find / -perm -4000 2>/dev/null` — пошук setuid-файлів
- `nc -l порт` — слухати порт (бути сервером)

## Головні висновки

- Перш ніж запускати незнайому програму з аргументами — запустити без них і прочитати, що вона очікує.
- `>` — завжди перенаправлення і завжди перезапис, де б воно не стояло.
- Опція і її значення стоять разом; порядок аргументів має значення.
- Мережа має два боки: хто підключається і хто слухає. Уміння бути і тим, і іншим — основа для розуміння атак.
- Права в Linux — це не лише `rwx`: `s` змінює те, з чиїми правами працює програма, і саме такі файли першими перевіряють при пошуку підвищення привілеїв.
