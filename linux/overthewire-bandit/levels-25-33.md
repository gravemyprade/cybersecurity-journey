## Level 25 → 26 — втеча з обмеженої оболонки через more і vi

**Завдання:** оболонка bandit26 — не `/bin/bash`, а щось інше. Зʼясувати, що це, і вирватися.

**Хід думок:**
Ключ до bandit26 лежав у домашній папці bandit25. Вхід із сервера на localhost тут заблокований (переконався в цьому ще на 14→15), тому забрав ключ на свою віртуалку через `scp` і дав йому `chmod 600`.

Коли зайшов, мене одразу викинуло назад. Спершу подумав, що щось не так із ключем, але швидко зрозумів: це і є суть рівня. Оболонка bandit26 показує текстовий файл через `more` і, щойно текст закінчується, виходить, а з нею закривається сесія.

Очікував, що просто треба «якось зайти». Насправді треба було зловити момент, коли `more` **не виходить**, а зупиняється і чекає. А `more` зупиняється лише тоді, коли текст не вміщається на екран. Сам файл я змінити не міг, зате міг змінити **розмір вікна**. Стиснув вікно терміналу до кількох рядків — банер перестав вміщатися, `more` зупинився з `--More--` і більше мене не викидав.

Далі згадав, що з `more` можна відкрити редактор `vi` клавішею `v`. А `vi`, на відміну від `more`, уміє виконувати команди. Через `:set shell=/bin/bash` і `:shell` запустив повноцінну оболонку — уже з правами bandit26.

**Що вивчив:**
- `more` виходить одразу, тільки якщо текст вміщається на екран; розмір вікна впливає на поведінку програми.
- Обмежену оболонку можна обійти через програму, яка вміє запускати інші команди (`more` → `vi` → `bash`).
- Такі «запасні виходи» з редакторів і переглядачів — класичний спосіб втечі з restricted shell.

## Level 26 → 27 — setuid-програма

**Завдання:** дістати пароль bandit27.

**Хід думок:**
Спочатку шукав SSH-ключ, бо на попередньому рівні був він. Але в домашній папці ключа не було — лише `text.txt` і файл `bandit27-do`. Це хороший урок: не діяти за припущенням, а дивитися, що є насправді.

`file bandit27-do` показав `setuid ELF`. Слово `setuid` одразу нагадало рівень 19→20: програма з таким бітом виконує команду від імені власника файлу. Тобто ця програма дає виконати будь-що від імені bandit27.

Пароль bandit27 лежить у `/etc/bandit_pass/bandit27`, і прочитати його може лише bandit27. Через `bandit27-do` я попросив програму зробити це замість мене.

**Що вивчив:**
- Перевіряти реальність, а не діяти за очікуванням.
- Setuid працює скрізь однаково: власник файлу довіряє програмі свої права.
- Той самий прийом, що й на 19→20, лише інший файл.

## Level 27 → 28 — перший git-репозиторій

**Завдання:** склонувати git-репозиторій і знайти пароль у ньому.

**Хід думок:**
Перша складність була не в git, а в адресі. Спершу написав `ssh:/` з одним слешем і дописав порт `2220` окремим словом у кінці. git не зрозумів адресу.

Розібрався, що порт у ssh-адресі належить **хосту**, тому ставиться одразу після імені сервера через двокрапку, а не наприкінці шляху і не окремим аргументом. Коли переписав адресу правильно (`ssh://...overthewire.org:2220/шлях`), клон пройшов.

Далі все просто: зайшов у склоновану папку, подивився файли — пароль лежав прямо у вмісті репозиторію.

**Що вивчив:**
- У ssh-адресі git порт іде після хоста: `host:порт/шлях`.
- `git clone` завантажує копію репозиторію разом з усією історією.
- Секрети в коді — реальна проблема; їх шукають у репозиторіях і пентестери, і захисники.

## Level 28 → 29 — пароль в історії комітів

**Завдання:** знайти пароль, хоча у файлі його немає.

**Хід думок:**
Склонував, відкрив `README.md` — а там замість пароля заглушка `xxxxxxxxxx`. Хтось його прибрав.

Згадав головну властивість git: він памʼятає історію всіх змін. Якщо пароль прибрали, він лишився в попередній версії файлу. Подивився історію через `git log` і побачив коміт `fix info leak` — промовиста назва, саме тут, найімовірніше, і «виправили витік», тобто замінили пароль.

Через `git show` на цьому коміті побачив, що саме змінилося, і дістав старий пароль.

**Що вивчив:**
- git памʼятає все; видалення секрету з файлу не прибирає його з історії.
- `git log` — історія змін, `git show` — що змінив конкретний коміт.
- Правильно скомпрометований секрет треба **міняти**, а не просто видаляти.

## Level 29 → 30 — пароль в іншій гілці

**Завдання:** знайти пароль, якого немає ні у файлі, ні в історії основної гілки.

**Хід думок:**
У README цього разу стояло `<no passwords in production!>` — у продакшен-гілці пароля навмисно немає. Історія теж нічого не дала.

Подумав про гілки. `git branch` показав лише `master`, але це локальні гілки. Щоб побачити й віддалені, додав `-a`. Серед гілок була `dev` — класична гілка розробки, де часто лежать робочі дані, яких немає в чистій продакшен-версії.

Подивився вміст README у гілці `dev` — пароль був там.

**Що вивчив:**
- `git branch -a` показує всі гілки, включно з віддаленими.
- Секрети ховаються не лише в історії, а й в окремих гілках (`dev`, `test`).
- Аудит репозиторію — це перевірка всіх гілок, не лише основної.

## Level 30 → 31 — пароль у тезі

**Завдання:** знайти пароль, якого немає у файлах, історії та гілках.

**Хід думок:**
README порожній, історія з одного коміту, гілки без нічого цікавого. Лишалося останнє місце, де git може щось зберігати, — теги.

Тег — це іменна позначка на коміті, якою зазвичай помічають версії релізу, але до нього можна причепити й текст. `git tag` показав один тег із назвою `secret` — назва сама за себе говорила. `git show secret` видав пароль.

**Що вивчив:**
- `git tag` — список тегів; `git show <тег>` — його вміст.
- Секрет може жити навіть у тезі. У git є чотири місця для схованки: файл, історія, гілка, тег.
- Для пошуку секретів існують окремі інструменти (gitleaks, truffleHog), які перевіряють усі ці місця.

## Level 31 → 32 — створити коміт і зробити push

**Завдання:** не прочитати репозиторій, а записати в нього файл.

**Хід думок:**
Тут уперше треба було не читати, а змінювати репозиторій. README чітко сказав: створити файл `key.txt` із вмістом `May I come in?` і запушити в гілку master.

Створив файл через `echo`. При `git add key.txt` git відмовився — файл потрапляв під `.gitignore`. git сам підказав рішення: додати з опцією `-f` (примусово).

На `git commit` вилізла нова перепона: git не знав, хто автор коміту. Він знову підказав — треба задати `user.email` і `user.name` через `git config`. Зробив це, закомітив, запушив — і пароль прийшов прямо у відповіді сервера на push.

**Що вивчив:**
- Повний цикл запису: `git add` → `git commit -m` → `git push`.
- `.gitignore` можна обійти через `git add -f`.
- git не дає комітити без заданого автора (`user.name`, `user.email`).
- Уважно читати повідомлення git — у них часто готове рішення.

## Level 32 → 33 — втеча з uppercase-оболонки

**Завдання:** вирватися з оболонки, яка все перетворює на великі літери.

**Хід думок:**
Зайшов — `WELCOME TO THE UPPERCASE SHELL`. Будь-яка команда перетворювалася на великі літери (`ls` → `LS`), а таких команд не існує, тому нічого не працювало.

Зрозумів, що оболонка псує саме **текст** команди. Отже, треба щось, що складається не з малих літер. Такими є спеціальні змінні оболонки з `$`. Шукав серед них ту, значення якої — сама оболонка.

Нею виявилася `$0` — імʼя поточної оболонки. Оскільки це цифра, uppercase її не псує. Ввів `$0`, оболонка підставила своє значення й запустила нову, нормальну оболонку — уже з правами bandit33. Запрошення змінилося з `>>` на `$`, і команди запрацювали.

**Що вивчив:**
- `$0` — імʼя поточної оболонки; через нього можна запустити нову.
- Якщо обмежена оболонка фільтрує ввід, але лишає доступ до змінних — замок обходиться.
- Фільтрувати треба все, включно зі спецсимволами та змінними.

## Головні висновки за рівні 25–33

- Обмежена оболонка — не глухий кут: якщо з неї можна запустити програму, що виконує команди (`vi`, `$0`), з неї виходять.
- git памʼятає все і скрізь: файл, історія, гілка, тег — секрет може бути в будь-якому з цих місць.
- Уважно читати вивід програм: і `more`, і git самі підказували наступний крок.
- Не діяти за припущенням — дивитися, що є насправді (26→27).
- Правильний інструмент для ресерчу: `man` для однієї опції, пошук — для цілого робочого процесу.
