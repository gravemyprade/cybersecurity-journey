# Конспект — Автентифікація та контроль доступу

> Identity, автентифікація, авторизація, протоколи, моделі доступу, IAM, NAC (Fortinet FCF). Базовий словник — у [[cybersecurity-fundamentals]], криптографія — у [[cryptography]], мережа — у [[secure-network]].

---

## Identity → Authentication → Authorization
Три кроки одного ланцюга, їх постійно плутають:

| Крок | Питання | Суть | Приклад |
|---|---|---|---|
| **Identification** | Хто ти? | **заявляєш** особу (ще не доведено) | логін, ID-картка |
| **Authentication** | Доведи | **підтверджуєш** заявлену особу | пароль, біометрія, токен |
| **Authorization** | Що тобі можна? | **права** вже підтвердженій особі | доступ до певних ресурсів |

- **Authentication ≠ Authorization:** можна бути автентифікованим (система знає, що це ти), але не авторизованим на дію (не дозволено).
- **Verification (1:1)** — звірка з одним заявленим записом. **Identification (1:N)** — пошук збігу серед усіх записів.
- **Accounting** — облік/логування дій (хто що робив). Разом: **AAA = Authentication, Authorization, Accounting**.

## Фактори автентифікації
- **Knowledge (знаю)** — пароль, PIN, Q&A.
- **Possession (маю)** — токен (hardware/software), смарт-карта, телефон, SMS, приватний ключ.
- **Inherence (є)** — статична біометрія: відбиток, обличчя, сітківка.
- **Behavior (як дію)** — динамічна біометрія: голос, keystroke dynamics.

> **MFA = комбінація факторів із РІЗНИХ категорій.** Два паролі ≠ MFA.

**OTP (one-time password)** для фактора «маю»:
- **HOTP** — лічильник-based (код міняється при кожному використанні).
- **TOTP** — час-based (код міняється кожні ~30с; Google Authenticator). Протухає сам → популярніший.
- Обидва = **спільний секрет + HMAC** ([[cryptography]]).

## Authentication framework
Чотири рівні абстракції — від задуму до заліза:
- **Method** — який підхід (категорії факторів, single vs MFA);
- **Form** — у якому вигляді доказ (пароль, OTP, сертифікат, біометрія);
- **Protocol** — як передати/перевірити (SAML, RADIUS, Kerberos…);
- **Tool** — чим реалізовано (Okta, authenticator-апка, RADIUS-сервер).

> **Протокол** = узгоджені правила розмови; існують на кожному рівні OSI. Auth-протоколи — L7, їдуть **поверх** TCP/IP (не замість).

## Протоколи автентифікації

### Федеративний SSO (веб/додатки)
- **SAML** — XML, корпоративний. SP ↔ IdP обмінюються підписаними **assertions** (authentication / attribute / authorization). SP не бачить пароль.
- **OAuth 2.0** — **авторизація, НЕ вхід**: дає апці обмежений доступ до твоїх даних на іншому сервісі без передачі пароля (токен).
- **OIDC** — шар **автентифікації поверх OAuth** (ID-токен, JWT). Механізм «Login with Google». Сучасний, JSON.

> OAuth = «що апці можна»; OIDC = «хто ти» поверх нього.

### Мережевий доступ / AAA
| | **RADIUS** | **TACACS+** |
|---|---|---|
| Для чого | доступ користувачів до мережі (VPN, Wi-Fi/802.1X) | адміністрування пристроїв (команди на роутерах/світчах) |
| Транспорт | UDP | TCP |
| Шифрування | лише пароль | увесь payload |
| A-A-A | об'єднує | розділяє |
| Вендор | стандарт | Cisco |

**RADIUS-потік:** `Client → NAS (authenticator) → RADIUS server → рішення`. Централізує автентифікацію; сам RADIUS зазвичай тримає креди не в себе, а питає **external repository** (SQL / **LDAP** / Active Directory). Двигун за **802.1X**.

### Корпоративний каталог
- **LDAP** — протокол доступу до каталогу (користувачі, групи). AD — LDAP-сумісний. Може автентифікувати (операція **bind**).
- **Kerberos** — **тикет-based** автентифікація (ядро AD): через довірену третю сторону **KDC** видаються тимчасові тикети → один вхід, багато сервісів (SSO). Пароль по мережі не передається. Взаємна автентифікація.
- У AD разом: **LDAP** = довідник, **Kerberos** = автентифікація.

### Методи (PPP / challenge-response)
- **PAP** — шле пароль **відкритим текстом**, two-way. Застарілий, небезпечний.
- **CHAP** — **challenge-response**: сервер шле випадковий виклик → клієнт відповідає `хеш(пароль + challenge)`, сам пароль не передається. Three-way, захист від перехоплення й replay. **MS-CHAP** — версія Microsoft.

### 802.1X — port-based network access control (PNAC)
Порт мертвий, поки пристрій не автентифікується. Три ролі:
- **Supplicant** — клієнтський пристрій;
- **Authenticator / Intermediary** — світч / AP (воротар, лише передає);
- **Authentication server** — RADIUS (виносить рішення).
Форми: логін+пароль або **цифровий сертифікат**.

**EAP (Extensible Authentication Protocol)** — рамка-обгортка, що дозволяє 802.1X використовувати різні методи. Через **TLS-тунель**:
- **EAP-TLS** — сертифікати з обох боків (найсильніший);
- **PEAP** — сертифікат лише на сервері, креди клієнта всередині TLS (найпоширеніший);
- **EAP-FAST** — PAC (креди від сервера) + TLS;
- **LEAP** — Cisco, старий, на WEP-ключах → **застарілий, не використовувати**.

## Single Sign-On (SSO)
Один вхід → доступ до багатьох сервісів.
- **Переваги:** менше паролів для юзера; менше адмін-навантаження (один набір кредів); простіший аудит/комплаєнс.
- **Недолік:** **єдина точка відмови** — скомпрометовані креди = доступ до **всього**.
- **Мітигація:** **MFA** на точці входу.

> **Session/SSO токени й cookies:** cookie — **контейнер/транспорт**, токен — **доказ входу** всередині. Крадіжка cookie = крадіжка сесії (session hijacking). Захист: HTTPS, прапорці HttpOnly, Secure.

## Моделі контролю доступу

| Модель | Рішення за | Хто задає | Характер |
|---|---|---|---|
| **DAC** (Discretionary) | на розсуд **власника** ресурсу | власник | гнучко, ризиковано |
| **MAC** (Mandatory) | за **мітками/класифікацією** | система централізовано (ніхто не змінить) | безпечно, жорстко |
| **RSBAC** (Rule-set) | за **набором правил** (src/dst/порт) | адмін (ACL) | як first-gen firewall / [[secure-network]] |
| **RBAC** (Role-based) | за **роллю** | адмін (ролі) | масштабно, корпоративний стандарт |
| **ABAC** (Attribute-based) | за **комбінацією атрибутів** (хто+що+коли+звідки) | rules engine | найточніше = zero-trust, але складно/дорого |

- **RBAC** — реалізація least privilege; мінус — час на проєктування ролей (role explosion).
- **ABAC** — технічна реалізація zero-trust (`Trust = Identity + Context`); атрибути: Personal (username, роль, IP), Resource (власник, розмір), Environmental (час, локація).

## IAM Life Cycle
У центрі — **Governance** (створює політики/ролі/групи + періодичний перегляд). По колу:
1. **Provisioning** — завести акаунт + призначити ролі/групи;
2. **Authentication** — перевірка особи;
3. **Authorization** — визначення прав + accounting;
4. **Self-service** — юзер сам: зміна пароля, оновлення даних, запит доступу, звіт про підозріле;
5. **Deprovisioning** — забрати права/ролі/доступ при звільненні.

> **Провалений deprovisioning → orphaned account** — активний «мертвий» акаунт, класичний вектор атаки. Ловиться періодичним переглядом.

## Виклики контролю доступу
- **Configuring** — складно налаштувати без помилок (дірки або блокування роботи);
- **Consistency** — однакові правила скрізь (неузгодженість = дірки);
- **User experience** — баланс безпека vs зручність (перекрутив → люди обходять);
- **Auditing** — єдиний «paper trail» для authn/authz, звести логи з розкиданих майданчиків і різних пристроїв докупи. Це по суті **SIEM**.

## Політики доступу

### Для користувачів
- **Reporting policy** — що логувати/звітувати;
- **Password policy** — довжина, складність, строк, блокування після N спроб;
- **Allowed use policy (AUP)** — що дозволено/заборонено робити з ресурсами.

> Політика каже «що треба»; технічний контроль (RADIUS/ACL/RBAC) її **примусово виконує**.

### Адміністратори / Governance
- **Duty Separation (SoD)** — ніхто один не контролює весь ланцюг (хто запитує ≠ схвалює ≠ видає). Проти зловживань.
- **Policy creation & recertification** — створювати й **періодично перезатверджувати** права (ловить privilege creep).
- **User Education** — навчання (людина — найслабша ланка).
- **Onboarding / Recertification / Offboarding** — IAM-цикл; offboarding критичний.
- **Escalation & Disaster Recovery Plans** — плани на інциденти/катастрофи.

## Файли та папки — успадкування
- **Inheritance** — права на папку успадковуються всіма вкладеними папками/файлами.
- Застосовувати права на папку **й усе під нею** (простота, максимальний захист).
- Уникати купи дрібних окремих прав; **консолідувати** файли з однаковими правами в одне місце.
- **Privilege creep** — поступове накопичення зайвих прав (перейшов між відділами — нові дали, старі не забрали). Лікується періодичним переглядом + чистою успадкованою структурою.
- Зламане успадкування (виняток на підпапці) = ризик, який треба бачити.

## NAC (Network Access Control)
Контроль хто/що потрапляє в мережу **за відповідністю вимогам безпеки**. Оцінює за: **User, Device, Location, Operating system** (+ posture) → будує **device profile**.

- **Походження:** виросло з **802.1X** (`Client → Authenticator → Authentication server`); форми — логін/пароль або сертифікат.
- **Модель доступу:** NAC застосовує **ABAC** (рішення за комбінацією атрибутів профілю).
- **Механізм enforcement:** після профілювання NAC наказує світчу **динамічно призначити VLAN** (або dACL) → пристрій потрапляє в потрібний сегмент. NAC *використовує* сегментацію, але сам = рішення, не поділ.
- **Профілювання:** за багатьма сигналами (802.1X головний; **MAC** лише для «тупих» IoT через MAB — слабкий, спуфиться; DHCP fingerprinting — підказка; posture). Не «DHCP видає профіль по MAC».
- **Сучасний NAC:** гранульований доступ за профілем **лише до потрібних ресурсів** (need-to-know = least privilege), а не бінарно «пустив/ні».
- **Виклики:** BYOD (особисті некеровані пристрої), IoT (роздувають attack surface) — драйвери «периметр помер».

> Траса зрілості: **802.1X → NAC → Zero-Trust** (від порт-контролю до постійної перевірки кожного запиту).
